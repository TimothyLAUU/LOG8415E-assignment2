# LOG8415E – Lab Assignment 2: Containerized Web Application on AWS

One orchestrator and two workers, deployed on AWS EC2 with Docker, Terraform and Bash.

- **Orchestrator** (Flask + gunicorn, port 80): receives `POST /new_request`, sends the request to a free worker, and queues it (FIFO) when both workers are busy.
- **Workers** (Flask in Docker, port 5000): run DistilBERT sentiment analysis and return JSON.
- **Infrastructure**: 3 Ubuntu 22.04 `t2.large` instances in `us-east-1`, created by Terraform. Docker is installed at boot by `user_data.sh`.

See `report.pdf` for the architecture, design explanations and results.

## Project structure


## Prerequisites

On your local machine (macOS or Linux; on Windows use WSL):

- [Terraform](https://developer.hashicorp.com/terraform/install)
- Python 3 (the test script uses only the standard library)
- `bash`, `ssh`, `scp`
- AWS Lab credentials configured in `~/.aws/credentials` 

You do **not** need to create an SSH key: `deploy.sh` generates `keys/lab-key` the first time it runs, and Terraform registers `keys/lab-key.pub` in AWS.

## How to launch the system

From the project root:

```bash
./deploy.sh
```

(If needed: `chmod +x deploy.sh`.)

The script stops at the first error and does the following:

1. Generates the SSH key if it does not exist.
2. Runs `terraform init` and `terraform apply` (3 instances, key pair, security group) and reads the IPs from the Terraform outputs.
3. Waits for each instance to accept SSH and to finish installing Docker (`/tmp/docker-ready`).
4. Copies `worker/` and `docker-compose.yml` to each worker and starts its container (`docker compose up -d --build`). Both workers are built **in parallel**.
5. Copies `orchestrator/` and `docker-compose.yml` to the orchestrator instance and starts its container, configured with the workers' **private** IPs.
6. Waits until both workers answer on `/health` (checked from the orchestrator, since port 5000 is not reachable from the Internet). This means the ML model is loaded.
7. Saves the orchestrator's public IP in `orchestrator_ip.txt`, prints `System ready at http://<ip>`, and runs `test_requests.py`.

### Expected runtime

A full deployment from scratch takes approximately **10 minutes**. Most of the time goes to booting the instances, installing Docker, building the PyTorch-based worker image, and downloading/loading the model on the first start. The test itself takes about 9 seconds (3 rounds of 3 s on 2 workers).

### Optional configuration

Terraform variables can be overridden with environment variables before running the script:

```bash
export TF_VAR_instance_type="t2.large"            # use the type given on Moodle
export TF_VAR_allowed_ssh_cidr="<your_ip>/32"     # restrict SSH (default: 0.0.0.0/0)
export TF_VAR_region="us-east-1"
./deploy.sh
```

## How to send a test request

The orchestrator address is saved in `orchestrator_ip.txt`.

**Concurrency test (6 requests, queue demonstration):**

```bash
python3 test_requests.py $(cat orchestrator_ip.txt)
```

Two requests are served immediately and four are queued. Expected wall time is about 9 s. The answers are printed and saved in `responses.json`.

**Single request with curl:**

```bash
curl -X POST http://$(cat orchestrator_ip.txt)/new_request \
     -H "Content-Type: application/json" \
     -d '{"text": "I love this course!"}'
```

Request body:

| Field            | Required | Description                                                      |
|------------------|----------|------------------------------------------------------------------|
| `text`           | yes      | Text to classify                                                 |
| `simulate_delay` | no       | Seconds the worker sleeps before answering (used to test queue)  |

Example response:

```json
{
  "queued": false,
  "wait_in_queue_s": 0.002,
  "worker": "worker1",
  "worker_response": {
    "input": "I hate waiting",
    "result": {"label": "NEGATIVE", "score": 0.9945},
    "worker": "worker1"
  }
}
```

`queued` is `true` and `wait_in_queue_s` is larger when the request had to wait for a worker.

**Status endpoint** (worker states and queue length):

```bash
curl http://$(cat orchestrator_ip.txt)/status
```


## How to stop and clean up AWS resources

**Always do this when you are finished**, to avoid consuming AWS credits:

```bash
cd terraform
terraform destroy -auto-approve
```

This deletes the 3 instances, the security group and the key pair. To only pause between work sessions, stop the instances from the AWS console instead; note that their public IPs change when they restart, so run `./deploy.sh` again.

## Troubleshooting

- **The script prints "waiting for workers to load the model ..." for a long time:** the first start downloads and loads the model. Check the logs:
  ```bash
  ssh -i keys/lab-key ubuntu@<worker_public_ip> "docker logs -f worker1"
  ```
  (use `worker2` on the second worker).
- **`502` in a response:** a worker did not answer (down, timeout or invalid reply). Check its container with `docker ps` and `docker logs`.
- **SSH waits forever:** check that `allowed_ssh_cidr` includes your current public IP.
- **Orchestrator logs:** `ssh -i keys/lab-key ubuntu@<orchestrator_ip> "docker logs -f orchestrator"`.

## Notes

- Ports: only 22 (SSH), 80 (orchestrator) and 5000 (workers, reachable only from within the security group) are open.
- The ML inference runs on the workers (DistilBERT, `distilbert-base-uncased-finetuned-sst-2-english`); the text-processing fallback is not used.
